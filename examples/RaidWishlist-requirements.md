# RaidWishlist Requirements

## Functional Requirements

### FR-RW-001 - Edit a wishlist in the addon
- **Status:** Verified Live
- **Source:** User decision, 2026-10-24.
- **Statement:** RaidWishlist MUST let the logged-in character add, change and remove wishlist entries in its window without importing a website export. An entry MUST have a positive numeric item ID, a main- or off-spec choice and an optional note; newly added entries follow the existing priority order and are shared with RaidLedger when sharing is enabled.
- **Rationale:** Raiders must be able to maintain a wishlist without visiting the guild website.
- **Security:** Item IDs and notes are player input. The addon MUST reject invalid IDs, bound note length and strip `|` before showing or sending a note (SC-019).
- **Acceptance criteria:** Given a valid item ID, spec and note, when the player saves it, then it appears in the wishlist and is persisted. Given a selected entry, when the player changes or removes it, then the saved list and shared wishlist reflect that change. Given a selected entry, when the player changes its item ID, then that entry gets the new ID and keeps its rank, and no second entry is added. Given a selected entry, when the player changes its item ID to one already on the list, then nothing changes and the window says the item is already on the list. Given an invalid item ID, when the player saves, then the list does not change and the window names the problem.
- **Evidence:** `examples/RaidWishlist/tests/manual_and_chat_reminder.spec.lua::manual entries can be created, changed and removed in the addon`; `::changing an entry's item ID replaces it; an ID already listed is refused` (fixed 2026-10-26: a changed ID used to add a second entry). Offline only. The editor save path also passed live in session `b98724ecb916` (bridge run `02ff188d50f8`); changing an item ID is offline only. Live session `4ed98683812d` (bridge run `ed3b1ec495d1`, 2026-10-26, plan `examples/RaidWishlist-edit-acceptance.json`) added items 20513 and 39247, changed the first to 40347, and the independent snapshot read exactly two entries (40347, 39247) with no Lua errors; `step-edited_list.png` shows them. Removing an entry and refusing an ID already listed are offline only.

### FR-RW-002 - Chat roll reminder
- **Status:** Verified Live
- **Source:** User decision, 2026-10-24.
- **Statement:** RaidWishlist MUST optionally show its existing roll prompt when a raid or party chat message from the master looter contains both a wishlisted item link and one configured reminder keyword. The default keywords are `roll` and `würfel`; players MAY change them and MAY allow all group senders instead of only the master looter. `/wish remind all` and `/wish remind master` MUST set the sender mode directly (the same setting as the settings page), so a repeated command or plan step leaves the same state.
- **Rationale:** A raid can announce rolls through chat or a different loot addon instead of RaidLedger.
- **Assumptions:** An external addon announces the item in a normal raid or party chat message. RaidWishlist cannot infer a roll window from an item link without a configured keyword.
- **Out of scope:** Parsing proprietary messages from other loot addons, deciding winners, and detecting a roll without an item link.
- **Security:** Chat is untrusted input. The addon MUST only inspect it as text, must not execute it, and must not create or modify wishlist data from it (SC-019).
- **Keyword matching:** Keywords are matched only in the message text outside item links, so an item name such as `[Trollbane]` never counts as the keyword `roll`. Messages that start with `[Loot]` are RaidLedger's own announcements (RaidLedger starts rolls by addon message, which RaidWishlist already answers); they never start a reminder, even when they contain a keyword (`is parked ... until it is rolled`, `free BoE roll won by`, `bis zum Auswürfeln`).
- **Acceptance criteria:** Given the default settings and a master-looter announcement containing a wishlisted item link plus `roll` or `würfel`, when the message arrives in party or raid chat, then the prompt appears. Given no matching keyword, a non-wishlisted item, or another sender while master-only mode is on, when the message arrives, then no prompt appears. Given a message whose only keyword match is inside an item link, or a RaidLedger `[Loot]` announcement, when it arrives, then no prompt appears and no automatic roll is made. Given changed keywords or all-senders mode, when a matching group message arrives, then the prompt follows those saved settings.
- **Evidence:** `examples/RaidWishlist/tests/manual_and_chat_reminder.spec.lua::chat reminders require a matching keyword and follow sender settings`; `examples/RaidWishlist/tests/chat_reminder_filters.spec.lua::a keyword inside an item name is no reminder`, `::RaidLedger announcements never start a reminder`, `::German keywords keep their umlauts when saved and still match` (fixed 2026-10-26: RaidLedger's parked, BoE and counted-roll announcements and item names such as `[Trollbane]` started prompts and auto-rolls; saved keywords were lowered, which mangled `ü`). Live session `d26c83592992` (bridge run `4b80e79fb9ad`, 2026-10-26, plan `examples/RaidWishlist-chat-reminder-acceptance.json`): with `/wish remind all`, the `master_loot` fixture's bot said `roll` plus a link to 40347 in party chat (Forge `peer_say`, FR-10.14), and the roll prompt opened for that wish (`step-chat_prompt.png`), with no Lua errors and no RaidLedger roll. Master-only mode, the keyword rules and the `[Loot]` filter are offline only, because the fixture's bot is never the master looter.

### FR-RW-003 - Search the WotLK raid catalogue
- **Status:** Verified Live
- **Source:** User decision, 2026-10-24; epic and higher only, user decision 2026-10-26.
- **Statement:** RaidWishlist MUST ship a fixed, searchable catalogue of loot items from Naxxramas, Obsidian Sanctum, Eye of Eternity, Ulduar, Trial of the Crusader, Onyxia's Lair, Icecrown Citadel and Ruby Sanctum. The catalogue MUST hold only items of epic quality or higher (item quality 4 or more); poor, common, uncommon and rare trash and world drops are left out. Searching by item name MUST show matching items with their raid and let the player add one directly to the wishlist.
- **Rationale:** Raiders must be able to create a wishlist without knowing numeric item IDs.
- **Locales:** The catalogue MUST search enUS and deDE item names and show the name for the current client locale.
- **Data source and license:** The catalogue is derived from AzerothCore WotLK world data (`item_template`, `item_template_locale` and loot templates), GPL-2.0. RaidWishlist is distributed under GPL-2.0 with a source attribution.
- **Security:** The search text is untrusted player input. It MUST be bounded, treated as plain text, and never executed or sent as an addon message (SC-019).
- **Acceptance criteria:** Given a German or English search term matching a catalogue item, when the player searches, then matching items from the eight named raids appear with their raid. Given a result, when the player selects and adds it, then it enters the wishlist with the selected spec and optional note, and the selection status does not overlap any editor control. Given an empty or non-matching query, when the player searches, then no item is added and the UI explains the result.
- **Evidence:** `examples/RaidWishlist/tests/catalogue.spec.lua::catalogue finds English raid loot and adds the selected result`; `examples/RaidWishlist/tests/catalogue.spec.lua::catalogue explains empty, unknown, and unsafe searches without adding an item`; `examples/RaidWishlist/tests/catalogue_german.spec.lua::catalogue finds localized German raid loot`. Live run `803ae5654d26` passed: the deDE client found the item from an English query, selected it, saved it as OS with the note `catalogue`, and the independent bridge snapshot confirmed the stored values with no Lua errors. `step-catalogue_selected.png` shows the non-overlapping selection status. Epic-only catalogue (2026-10-26, offline): `examples/RaidWishlist/tests/catalogue.spec.lua::the catalogue holds only epic and legendary loot`; 365 poor-to-rare items removed, 1,802 remain. The live runs above used the earlier 2,167-item catalogue. Live session `be98ebf63a65` (bridge run `eb3281e972e4`, 2026-10-26) passed on the epic-only catalogue: the deDE client found item `39247` and saved it as OS with note `catalogue`, with no Lua errors. That non-epic items are absent is checked offline only (the shipped data is fixed).

### FR-RW-004 - Set current Enhance points
- **Status:** Verified Live
- **Source:** User decision, 2026-10-24.
- **Statement:** RaidWishlist MUST let the logged-in character set their current Enhance-point balance on the settings page. The value MUST persist per character, replace the previous current balance, reset locally tracked Enhance spending, and determine the bonus used by later enhanced main-spec rolls.
- **Rationale:** Raiders who do not import a website export still need correct enhanced-roll ranges.
- **Security:** The value is local player input. It MUST be a bounded non-negative integer; an invalid value MUST leave the saved balance unchanged (SC-019).
- **Shown value:** The settings page MUST show the current balance (the saved balance minus locally tracked Enhanced spending), not the roll bonus capped at 50, so saving without a change never lowers the balance.
- **Spending cutoff:** Enhanced wins count against the balance only when they happened after that balance was set (the export time for an import, the save time for typed points). Editing wishlist items MUST NOT move that cutoff, so a later award correction neither refunds nor charges a win twice.
- **Acceptance criteria:** Given an Enhanced win counted against the balance, when the player edits a wishlist item and the win's award is corrected later, then the win still counts once. Given typed points, when an earlier win's award is corrected later, then it is not charged again. Given an imported balance of 70, when the player opens Settings and saves without typing, then the balance stays 70. Given a valid point value, when the player saves it, then it survives reload and an enhanced main-spec wishlist roll uses `1 + min(points, 50)` through `100 + min(points, 50)`. Given an invalid value, when the player saves, then the balance remains unchanged and the editor explains the error.
- **Evidence:** `examples/RaidWishlist/tests/enhance_points.spec.lua::current Enhance points are saved per character and set the enhanced roll range`; `::invalid Enhance points leave the current balance unchanged`. Live run `339f0aff9731` (bridge run `dfc9537f7cb7`) saved 37 points from the settings page; the independent bridge snapshot read `RaidWishlistDB.chars.Test.balance = 37`, with no Lua errors. Fixed 2026-10-26 (offline): `::the settings page shows the real balance, so saving it unchanged keeps 70` (the field showed the capped bonus and saving cut 70 to 50); `examples/RaidWishlist/tests/enhanced.spec.lua::editing an item refunds nothing; set points are not charged for older wins` (`balanceAt` now holds the spending cutoff instead of `exportedAt`). After the fix, live session `b98724ecb916` (bridge run `02ff188d50f8`, 2026-10-26) passed the catalogue plan on the fixed build: SET POINTS saved 37, the catalogue item was saved as OS with note `catalogue`, no Lua errors. That plan does not exercise the fixed behaviour itself (shown balance, SAVE SETTINGS, CANCEL). Live session `4ed98683812d` (bridge run `ed3b1ec495d1`, 2026-10-26, plan `examples/RaidWishlist-edit-acceptance.json`) imported a balance of 70; the settings page showed 70 (`step-settings_balance_70.png`) and SAVE SETTINGS kept balance 70 in the independent snapshot. The spending cutoff (`balanceAt`) is offline only.

### FR-RW-005 - Dedicated settings page
- **Status:** Verified Live
- **Source:** User decision, 2026-10-24.
- **Statement:** RaidWishlist MUST show Enhance points and chat roll-reminder controls on one dedicated settings page, separate from the wishlist-item editor. The player MUST be able to open that page from the main window and while editing an item.
- **Rationale:** Character preferences must not be confused with the attributes of one wishlist item.
- **Saving:** SAVE SETTINGS saves every setting on the page at once (Enhance points, sender mode and keywords); an invalid value saves nothing and names the problem. CANCEL discards every unsaved change, including the sender-mode button. SET POINTS remains a shortcut that saves only the points.
- **Acceptance criteria:** Given the main window or an open item editor, when the player opens Settings, then the settings page shows both Enhance points and chat roll-reminder controls. Given the editor, then it contains no Enhance-points or reminder-setting controls. Given typed points and SAVE SETTINGS, then the points are saved. Given a changed sender mode and CANCEL, then the saved sender mode is unchanged.
- **Evidence:** `examples/RaidWishlist/tests/enhance_points.spec.lua::current Enhance points are saved per character and set the enhanced roll range`; `examples/RaidWishlist/tests/german.spec.lua::every German editor and settings button fits its panel`; `examples/RaidWishlist/tests/manual_and_chat_reminder.spec.lua::chat reminders require a matching keyword and follow sender settings`. Live run `339f0aff9731` (bridge run `dfc9537f7cb7`) opened Settings from the editor, set points and recorded `step-reminder_settings.png`. Fixed 2026-10-26 (offline): `examples/RaidWishlist/tests/enhance_points.spec.lua::SAVE SETTINGS saves typed points; CANCEL discards the sender mode`, `::an invalid value on the settings page saves nothing` (the sender-mode button used to save at once, and SAVE SETTINGS ignored typed points). After the fix, live session `b98724ecb916` (bridge run `02ff188d50f8`, 2026-10-26) passed the catalogue plan on the fixed build: SET POINTS saved 37, the catalogue item was saved as OS with note `catalogue`, no Lua errors. That plan does not exercise the fixed behaviour itself (shown balance, SAVE SETTINGS, CANCEL). Live session `fe3ce425ea29` (bridge run `9d718e6168bd`, 2026-10-26, plan `examples/RaidWishlist-settings-acceptance.json`) saved typed points 42 with SAVE SETTINGS, then typed 50 and pressed CANCEL; the independent snapshot read balance 42, with no Lua errors.

### FR-RW-006 - Filter and inspect catalogue results
- **Status:** Verified Live
- **Source:** User decision, 2026-10-25.
- **Statement:** RaidWishlist MUST let the player choose raid and item-quality filters from drop-down menus for catalogue search results, and show the normal item tooltip when the pointer is over a result. The quality menu offers only the qualities the catalogue holds: all, Epic and Legendary.
- **Rationale:** A player needs to narrow common item-name searches and inspect an item's effects before adding it.
- **Acceptance criteria:** Given active raid and quality filters and a matching item-name search, when the player searches, then only entries matching both filters appear. Given a result, when the player hovers it, then the client item tooltip is shown.
- **Evidence:** `examples/RaidWishlist/tests/catalogue.spec.lua::catalogue drop-down filters results by raid and quality and shows an item tooltip`; `examples/RaidWishlist/tests/bridge_registration.spec.lua::all registered wishlist controls satisfy the bridge contract`. Live run `95d4d1897cfe` (bridge run `4eebb4f03c39`) selected Naxxramas and Episch from the drop-down menus, found item `39247`, saved it as OS with note `catalogue`, and recorded `step-catalogue_results.png` and `step-catalogue_selected.png` without Lua errors. Since 2026-10-26 the quality menu offers only all, Epic and Legendary, so Epic is `RaidWishlistCatalogueQ2` (was `Q6`); the plan was renamed to match, and the run above predates that. Offline: `::catalogue drop-down filters results by raid and quality and shows an item tooltip`. Live session `be98ebf63a65` (bridge run `eb3281e972e4`, 2026-10-26) clicked Naxxramas and the new Epic button `RaidWishlistCatalogueQ2`; `step-catalogue_results.png` shows `Episch` and one result, with no overlap and no Lua errors.
